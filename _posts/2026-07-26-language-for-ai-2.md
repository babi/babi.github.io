> 接上篇，这篇是 ChatGPT 对同一问题的深度分析，从工程化治理的角度探讨了"自然语言作为系统定义"的结构性风险和对策。

---

## 1. 自然语言系统最大的风险：局部可读、整体不可推理

自然语言定义的最大问题是——**局部可读、整体不可推理**。

一段技能描述可能看起来清晰，但当多个技能叠加、多个 sub-agent 协作时，整体行为无法从这些片段的文本中推导出来。比如：

- 继承规则不明确
- 冲突解决规则缺失
- 前置条件松散
- 后置条件未定义

结果是，每个单独的定义都读得懂，但系统整体的行为不可预测。

---

## 2. 未来更合理的方向：自然语言前端 + 结构化中间表示

最终形态应该类似编程语言的**编译过程**：

```
人类自然语言 → 规范化定义 → 中间表示 → 执行计划 → 运行与验证
```

自然语言负责表达意图，结构化表示负责确保确定性。

例如，用户或设计者可以写：

> *当用户询问最新的软件版本时，优先查官方文档。如果无法找到官方信息，再使用可靠的第三方来源。不要仅凭模型记忆回答。*

系统不应直接执行这段文字，而应该把它**编译**成类似这样的规则：

```yaml
trigger:
  topic: software_version
  freshness_required: true

actions:
  - search:
      source_priority:
        - official_documentation
        - official_repository
        - trusted_third_party

constraints:
  memory_only_answer: prohibited

fallback:
  on_no_authoritative_source:
    response: disclose_uncertainty
```

这并不意味着所有人都要写 YAML。用户仍然可以使用自然语言，但系统内部应该有一个**稳定、可验证、可比较的中间表示**。

也就是说：

> **自然语言是 UI，不是 IR。**

---

## 3. 一个 Skill 至少应该分成五层

### 第一层：意图说明

回答"为什么存在"。

例如：

> 用于分析实验结果，并生成包含假设、方法、结果和结论的报告。

这一层可以自由使用自然语言。

### 第二层：接口契约

回答"输入和输出是什么"。

需要结构化定义：

- 必需输入
- 可选输入
- 输出格式
- 类型
- 默认值
- 最大长度
- 是否允许缺失

### 第三层：行为规则

回答"在什么条件下做什么"。

最好使用**受控表达**：

```
WHEN 数据包含对照组
THEN 计算组间差异

WHEN 缺少样本量
THEN 标记统计结论不完整

NEVER 推断未提供的实验数据
```

这种"受控自然语言"比完全自由的散文更适合作为规则。

### 第四层：执行能力和权限

回答"允许做什么"。

例如：

- 可访问哪些工具
- 是否可以联网
- 是否可以写文件
- 是否可以发送邮件
- 是否允许创建子 Agent
- 最大调用次数
- 成本和时间限制

**权限不应该隐藏在描述性文本中。**

### 第五层：验收标准

回答"怎样才算正确"。

一个 Skill 不应该只有 Instructions，还应该包含**测试用例**：

```yaml
tests:
  - input: "分析这份没有对照组的数据"
    expected:
      - identify_missing_control_group
      - avoid_causal_claim

  - input: "编造缺失的样本量"
    expected:
      - refuse_fabrication
```

这会把 Skill 从"提示词文档"变成真正的**可测试组件**。

## 4. 需要标准化的不是措辞，而是语义槽位

很多团队会尝试通过 Prompt 模板统一写法，例如规定所有人必须使用：

```
Role
Goal
Instructions
Constraints
Examples
```

这有帮助，但还不够。

因为大家即使使用相同标题，仍然可能表达完全不同的语义。

真正需要标准化的是一些**系统级概念**：

| 语义槽位 | 要回答的问题 |
|---|---|
| **Trigger** | 什么时候调用？ |
| **Scope** | 处理什么，不处理什么？ |
| **Inputs** | 需要哪些信息？ |
| **Outputs** | 返回什么？ |
| **Preconditions** | 执行前必须满足什么？ |
| **Invariants** | 执行过程中始终不能违反什么？ |
| **Decision rules** | 不同条件下如何选择？ |
| **Permissions** | 可以使用哪些资源？ |
| **Failure policy** | 失败时怎么处理？ |
| **Escalation** | 什么时候交给人或上级 Agent？ |
| **Tests** | 如何证明行为正确？ |
| **Version** | 规则属于哪个版本？ |

人们可以使用不同措辞，但必须填写相同的**语义槽位**。

这类似于数据库：字段里的文本可以不同，但**表结构必须稳定**。

## 5. 要把"描述性文字"和"规范性规则"分开

自然语言文档中最容易混乱的一点，是无法区分：

- 建议
- 偏好
- 默认行为
- 强制要求
- 禁止行为

例如：

> 尽量保持回答简洁，但需要确保完整性。必要时可以展开。

这对人类来说很自然，但对执行系统来说**几乎没有约束力**。

更好的做法是引入**规范级别**：

| 级别 | 含义 |
|---|---|
| **MUST** | 必须执行 |
| **MUST NOT** | 禁止执行 |
| **SHOULD** | 默认执行，可以有理由地偏离 |
| **MAY** | 可选 |
| **PREFER** | 多个合法选项中的偏好 |

并要求每条规则具备**唯一 ID**：

```
R-101 MUST 使用官方来源验证当前版本。
R-102 MUST NOT 在没有来源时声称版本是最新的。
R-103 SHOULD 优先返回稳定版本，而不是测试版本。
```

这样才能支持：

- 冲突检测
- 引用追踪
- 修改审计
- 测试映射
- 版本管理

## 6. Subagents 还需要"组织协议"

Subagents 不只是多个 Prompt，它们本质上构成了一个**组织**。

只定义每个 Agent 的角色，却不定义它们之间的关系，就像招聘了很多员工，却没有组织架构和决策流程。

至少要明确：

- 谁负责拆解任务
- 谁拥有最终决策权
- 谁可以否决谁
- 子 Agent 能否调用其他 Agent
- 信息如何传递
  - 是传递原始上下文，还是结构化摘要
- 冲突如何裁决
- 失败如何重试
- 什么时候升级给主 Agent
- 谁对最终结果负责

一个成熟的多 Agent 系统，核心可能不是 Agent Prompt，而是它们之间的**协议**：

| 角色 | 职责 |
|---|---|
| **Planner** | 产生任务计划 |
| **Executor** | 只能执行计划中明确授权的步骤 |
| **Reviewer** | 不修改结果，只输出问题列表 |
| **Planner（再）** | 根据 Reviewer 结果决定重新执行或提交 |
| **Finalizer** | 唯一可以向用户输出最终答案的角色 |

这类协议应尽可能**形式化**，而不是散落在多个 Agent 的描述中。

## 7. 自然语言的差异并非全是坏事

这里也需要避免走向另一个极端。

自然语言的灵活性有非常大的价值：

- 可以表达复杂意图
- 容易被非程序员理解
- 易于快速迭代
- 能处理边界模糊的任务
- 可以表达价值判断和上下文
- 比传统 DSL 更适合开放世界问题

**问题不是消灭自然语言，而是为它增加"护栏"。**

可以把系统内容分成两个区域：

### 柔性区域

允许自由表达：

- 背景
- 目的
- 用户体验
- 写作风格
- 典型案例
- 解释性说明

### 刚性区域

必须结构化：

- 输入输出
- 权限
- 状态转换
- 触发条件
- 禁止事项
- 失败策略
- 安全边界
- 决策优先级
- 验收标准

> **最危险的情况，是用柔性的语言定义刚性的系统行为。**

## 8. 管理上的重点会从"写 Prompt"转向"治理语义"

未来团队中可能会出现一种类似 **"Agent 架构师"** 或 **"语义工程师"** 的角色。其工作不是单纯优化措辞，而是负责：

- 建立规则本体
- 定义标准术语
- 设计 Skill 接口
- 维护规则优先级
- 管理能力和权限
- 建立测试集
- 分析执行轨迹
- 处理版本兼容
- 监控行为漂移

这和早期软件开发非常相似。

早期程序员可以随意写机器码；后来逐渐产生：

```
编程语言 → 类型系统 → 模块系统 → 接口定义 → 单元测试
→ CI/CD → 代码审查 → 包管理 → 权限模型
```

Agent / Skill 生态大概率也会经历同样的演化。

> 现在很多所谓 Skill，实际上还处于"脚本时代"。

---

## 9. 一个可操作的治理框架

对于正在构建 Skills 或 Subagents 的团队，以下三层机制值得参考：

### 设计时：规范化

每个组件必须提供：

- 结构化 Manifest
- 自然语言说明
- 输入输出 Schema
- 权限声明
- 至少三个正向测试
- 至少三个边界或反向测试
- 版本号和负责人

### 发布时：静态检查

系统自动检查：

- 是否存在互相冲突的 MUST 规则
- 是否存在未声明的工具调用
- 是否有无限递归调用风险
- 是否缺少失败处理
- 是否有无法测试的模糊词汇
- 输出是否符合 Schema
- 新版本是否破坏兼容性

例如，对这些词做**警告**：

> 适当 / 必要时 / 尽可能 / 合理 / 一般情况下 / 根据情况 / 高质量 / 充分 / 及时

这些词不是不能出现，但出现时应要求补充判断标准。

### 运行时：可观察和可验证

记录：

- 哪条规则被触发
- 哪个 Agent 做了决定
- 使用了哪些输入
- 调用了哪些工具
- 为什么选择这一分支
- 哪些约束被检查
- 哪些规则发生冲突
- 最终结果通过了哪些验证

> **没有运行轨迹，规则系统就无法真正治理。**

---

## 10. 最终会形成"自然语言操作系统"，但其内核不会是自然语言

趋势不会停止。人们会越来越多地使用自然语言定义：

- 工作流
- 自动化
- Agent
- 权限
- 数据处理
- 业务规则
- 软件行为

但成熟系统不会直接把所有自然语言拼接成一个超级 Prompt。

更可能的架构是：

```
自然语言意图
    ↓
语义解析与消歧
    ↓
结构化规则 / 中间表示
    ↓
静态检查与权限验证
    ↓
执行图
    ↓
运行时监督
    ↓
结果验证
```

**自然语言负责降低表达门槛，形式化系统负责控制复杂度。**

---

## 我的结论

这个趋势确实存在结构性风险，但不意味着自然语言不适合描述系统。

更准确地说：

> **自然语言适合描述"我们想要什么"，不适合单独保证"系统一定如何执行"。**

未来的关键不是找到一种"完美 Prompt 写法"，而是建立一种混合范式：

- **自然语言**负责意图
- **Schema** 负责接口
- **规则语言**负责约束
- **测试**负责语义
- **运行时**负责监督
- **版本系统**负责演进

当一个 Skill 只有自然语言说明时，它更像一份**员工入职指南**；当它拥有接口、权限、测试、版本和运行轨迹时，它才真正成为一个**工程化的软件组件**。
